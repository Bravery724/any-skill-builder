# Independent design review

The questions resolve distinct choices, and the selected answers have visible effects in `weekly-team-update/SKILL.md`:

- `readers` controls assumed project knowledge. The selected `cross-functional` answer appears as “Explain project terms that cross-functional readers would not recognize.” The routine output explains staging as “the pre-production test environment”; the conflicting output explains a feature flag as a switch controlling availability.
- `evidence` controls source placement, independently of audience. The selected `inline` answer appears as “Put supplied source links beside the claim they support and use descriptive link text.” Both outputs keep the issue link beside the relevant change or unresolved status. This demonstrates placement and preservation, not verification of the fictional destinations.
- `missing-information` controls whether material gaps delay the final draft. The selected `draft-gaps` answer appears as “The selected workflow is to produce a useful draft first.” The routine output leaves production approval and the access-request owner unresolved; the conflicting output preserves both incompatible release claims and the unaccepted Wednesday proposal.

The source reasoning is appropriately limited. I inspected the relevant sections of the [GitLab Communication handbook](https://handbook.gitlab.com/handbook/communication/): internal communication guidance calls for explicit context, and issue cross-linking guidance calls for a preview of linked content. These support the rationale behind `readers` and `evidence`. Choosing these exact questions, defaulting to cross-functional readers, and preferring inline links remain design inferences, not results established by the handbook. `questionnaire.json` correctly labels those questions as `inference`; it labels `missing-information` and `clarification-trigger` as `proposal` with no claimed source. `research.md` also explicitly limits the source review and disclaims evidence of completeness or superiority. The decisions are identified as authored example choices, not a live user's answers.

If `missing-information` changed to `clarify-first`, `clarification-trigger` should become active because its condition is `missing-information == clarify-first`. With the current `draft-gaps` choice, it should stay inactive, as recorded in `decisions.json`. Its recommended answer is only a proposed threshold, not an already selected answer. Once the blocking facts are selected, the generated skill would need to replace draft-first handling with focused questions before the final draft when those facts are missing; changing the answer alone does not rewrite this existing skill file. If the recommendation were accepted, the conflicting case would require clarification of release status and the unconfirmed rollout commitment. The routine case would need assessment against that threshold: the access-request owner is missing, but the input does not establish an urgent request, and pending approval is not itself a contradictory status. Minor omissions would not automatically block either case. This alternative workflow has not been generated or executed here.

A material remaining gap is audience authorization for sensitive content. The questionnaire assumes recipients may read the supplied material, while the skill restricts reading to authorized material and says not to publish unless asked. Neither defines what to omit when authorized input contains facts unsuitable for some recipients. That needs a concrete decision and evaluation case before extending this example to mixed-access reporting. The present fictional drafting cases do not establish exhaustive coverage, publication safety, or improvement over a baseline.
